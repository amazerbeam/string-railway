## Step 0: Preconditions — only refuse when there is literally no context

The gate is narrow. Only refuse to plan if one of these two unrecoverable conditions holds:

1. **No brief** — `$ARGUMENTS` is empty and there is no pasted task description, spec, or file reference in the session.
   - Response: "Describe the task before invoking `/fb-plan`."

2. **Brief unreadable** — the developer named a spec file, contract folder, or source file and it cannot be read (missing path, permission error).
   - Response: surface the actual error verbatim and list what you did find (e.g. the specs that exist under `.claude/contract/specs/`). Ask the developer to paste the brief inline or fix the path. Do not guess.

**Vagueness is NOT a refusal condition.** If the brief is missing pattern references, ambiguous on scope, light on technical pointers, or otherwise sparse — proceed. Do not bounce it back to the developer. Instead, in Step 2:

- Make the **most plausible decisions** you can defend, drawing on the loaded skills (Step 1.5) and the conventions they encode.
- Capture every such decision in the **"Assumptions made"** section of `plan.md` Part 1, each with a one-line rationale.
- Frame the plan so the developer can red-line specific assumptions during Part 1 review rather than rewriting the brief.

The alignment check happens in `plan.md` Part 1, not at the gate. A best-effort plan with explicit assumptions is more useful to the developer than a refusal.

## Step 1: Defer to the workflow reference, the skills, and the shared rules

- **Read `.claude/workflow/unity-project.md` first, every time.** It is the canonical statement of where code lives, which commands verify it, what only the developer can do in the Editor, and the Unity-specific traps (serialized-field renames, fake-null, lifecycle ordering, per-frame allocation). Every `Run:` step you write and every path you name must come from it. If a path there turns out to be wrong, fix *that* file rather than working around it in the plan.
- **Never pattern-match against generated output.** `Library/`, `Temp/`, `Logs/`, `Build/`, `obj/`, `*.sln`, and `*.csproj` are regenerated by Unity from the real source. They are not evidence of anything and must never be planned as edit targets. Imported third-party code (`Assets/Plugins/`, `Assets/ThirdParty/`, anything from the Asset Store) is vendored — do not pattern-match against it and do not plan an edit to it unless the brief names it explicitly.
- **Read the shared rules that apply.** Scan `.claude/rules/README.md` and Read every rule file whose topic the plan touches. Their **reject conditions** are planning constraints: a plan that would trip one is a broken plan. That folder may be empty — an empty scan is a valid outcome, not a reason to stop.
- **Quality standards** live in the skills (where one exists for the area) and in `CLAUDE.md` at the repo root, which holds the project-wide conventions.

If the brief points to specific files, components, or prefabs as a pattern reference, treat those as authoritative for this task.

## Step 1.5: Classify the work and load skills BEFORE planning

The planner is only as good as the conventions it has loaded. Without the right skills in context, plans can be internally consistent yet land in the wrong assembly, miss house naming, or ignore a Unity lifecycle constraint. Close that gap before writing either file.

### a) Discover which skills actually exist

**Do not classify against a remembered roster.** Glob `.claude/skills/*/SKILL.md` and read the `description:` line of each hit. That listing is the real menu.

At the time this workflow was installed the only skill present was `skill-creator` — this project has **no domain skills yet**. That is expected for a new project and is not a blocker. It does change what this step produces:

- If a skill covers the area the brief touches, propose it.
- If none does, say so plainly in `plan.md` Part 2 under "Skills to invoke during execution" — write `none — no skill covers <area> yet` rather than naming a skill that does not exist. A plan that tells the executor to invoke a missing skill wastes a turn and erodes trust in the whole list.
- If the area will clearly recur (the third task in a row that needs the same unwritten conventions), note it as a follow-up: `/skill-creator` is the way to write that skill, and it is its own piece of work, not something to smuggle into this plan.

### b) Classify the work from the brief

Pick every category that applies; a task can be in more than one.

**Code** — anything under `Assets/Scripts/`. Sub-classify by what it actually touches, because it changes the risk profile and therefore the plan:
- **Pure C# logic** (no `UnityEngine` types, no `MonoBehaviour`) — fully unit-testable in EditMode. Prefer pushing logic here.
- **`MonoBehaviour` / component code** — subject to lifecycle ordering, fake-null, and per-frame cost. Needs the traps section of `unity-project.md`.
- **`ScriptableObject` / data assets** — changing a serialized field affects every existing asset instance on disk.
- **Editor code** (`Assets/Scripts/Editor/` or any asmdef with `includePlatforms: Editor`) — never ships in a build; must not be referenced from runtime code.

**Assets and project state** — scenes, prefabs, `ProjectSettings/`, Input System actions, Addressables groups. Largely **developer-owned Editor work** (see `unity-project.md`), so these become paused hand-off tasks rather than Implementer tasks.

**Process** — the developer wants a standalone spec document before code, or the brief is still too vague to plan. Say so rather than planning blind.

### c) Confirm the skill list with the developer

Build the proposed list from (a) and (b), then call `AskUserQuestion` **once** to confirm — a single `multiSelect: true` question listing the matched skills, each option's description naming what that skill owns for this task. `AskUserQuestion` allows at most 4 options per question; if the classification matched more, ask a second question in the same call. The developer can untick anything that doesn't apply or tick extras the classifier missed.

**Skip this call entirely when the classification matched no skills** — an `AskUserQuestion` with nothing to choose between is noise. Record `none` in Part 2 and move on. If the runtime cannot present `AskUserQuestion` (non-interactive session), proceed with the proposed list and note in `plan.md` Part 2 that no developer override was applied.

### d) Load the confirmed skills

For each confirmed skill, invoke it via the `Skill` tool *before* writing `plan.md` and `tasks.md`. The skill content informs:
- the **Approach** section in `plan.md` Part 2 (correct assembly placement, correct patterns)
- the file paths each task names (right paths, right naming)
- the **Tasks** in `tasks.md` (concrete steps that match house standards)

Record the loaded skills in `plan.md` Part 2 under "Skills to invoke during execution" — this becomes the handoff list for the post-`/clear` execution session. If the developer overrode a skill, capture that in a one-line note under the list so the execution session understands why.

## Step 1.6: Serialization and asset-reference audit (when applicable)

Unity's real integrity risk is not a database — it is **serialization**. Scenes, prefabs, and `ScriptableObject` assets store references by GUID and serialized fields by name, on disk, outside the compiler's view. A rename that compiles cleanly can silently null out an Inspector reference on fifty prefabs. Ground the plan in the actual on-disk state before designing.

Run this step whenever the task touches a `[SerializeField]` field, a `MonoBehaviour` or `ScriptableObject` class name, a prefab, a scene, or an asset reference. Skip it entirely for pure-C# logic with no serialized surface, no `UnityEngine` types, and no asset involvement — and say so in one line.

Use `Grep`, `Glob`, and `Read` against the real files (scenes and prefabs are YAML; `.meta` files are YAML). Confirm:

1. **Every field being renamed or removed is found by name** across `Assets/**/*.prefab`, `Assets/**/*.unity`, and `Assets/**/*.asset`. Quote the actual hit count. A field with hits needs `[FormerlySerializedAs]` in the plan; a field with zero hits is safe to rename outright, and knowing which is which is the point of the audit.
2. **Every class being renamed matches its filename**, and the file's `.meta` GUID is the one scenes and prefabs reference. Grep the GUID to find every consumer. A `MonoBehaviour` whose class name and filename diverge is already broken — that is an in-scope defect, not an out-of-scope item.
3. **Type changes on serialized fields are checked for loss.** `int` → `float` widens cleanly; `float` → `int` truncates every existing asset; changing a field from a value type to a reference type discards the data entirely. State which case applies and, if lossy, what the plan does about it.
4. **Every `ScriptableObject` asset instance affected is enumerated** — `Glob Assets/**/*.asset` and grep for the script GUID. "Some assets may be affected" is not an audit; a count is.
5. **Names align across the chain**: serialized field name ↔ the name in the prefab/scene YAML ↔ any save-data key ↔ any Animator/Input action string. Unity binds several of these by *string*, so the compiler will not catch a mismatch. Any mismatch found is an in-scope defect.
6. **Scenes the change depends on are in Build Settings.** Read `ProjectSettings/EditorBuildSettings.asset`. A scene absent from that list cannot be loaded at runtime, and the failure appears only in a player build — well after review.

Capture findings in `plan.md` Part 1 under **"Serialization and asset-reference audit"**, one bullet per check, quoting real counts and real GUIDs. An audit that paraphrases instead of quoting has not been done.

2. Create `.claude/contract/<slug>/`. For the rest of this document, `<plan>` means that path.

## Step 2.5: Self-review plan.md

Before handing off for approval, review `plan.md` against the brief. No subagent dispatch — do this yourself.

1. **Brief coverage:** Skim each requirement and pattern reference in the brief. Is each reflected in Part 1 → In scope and addressed in Part 2 → Approach? List gaps and fix.
2. **Structural completeness:** Exactly two `##` parts and fourteen `###` sections, in the template's order — counting only headings **outside** fenced code blocks. A plan that documents a markdown template embeds headings inside a fence; those belong to the example, not to the document, and a naive `Select-String '^## '` count will fail on them. Each is filled or carries an explicit one-line skip justification. No heading inside a section is a `###`.
3. **Placeholder scan:** No `TBD`, `TODO`, `implement later`, "appropriate error handling", empty `mermaid` fences, or empty sections. Fix every hit.
4. **Assumptions ↔ design alignment:** Every assumption in Part 1 that constrains a technical decision is reflected in Part 2 → Approach or Risks and judgement calls. Assumptions that influence nothing are noise — drop them.
5. **Serialization audit (when Step 1.6 ran):** The audit section reports a finding for every check performed, with real counts. Every renamed serialized field with non-zero hits has `[FormerlySerializedAs]` in Data shapes.
6. **Skill list honesty:** Every skill named in Part 2 resolves to a real `.claude/skills/<name>/SKILL.md`. No invented skills.
7. **Rule compliance:** No reject condition from any applicable `.claude/rules/` file is tripped by the design.

Fix issues inline. Continue to Step 3.

**Rules for tasks.md:**

- Tasks are grouped under `## Phase N — Name` headings. Phase numbering starts at 1; task numbering is sequential across all phases.
- Every phase opens with a 1-3 sentence framing paragraph explaining what the phase covers and why the boundary is a safe stopping point.
- **Never plan commits.** No `git commit` steps, "commit at end of phase" instructions, or commit-message templates. Committing is the executor's decision.
- Every code-touching task carries a `**Files:**` block and at least one `- [ ] **Step:**` bullet.
- **Step shape is flexible — fit the work, not a fixed template.** Common shapes:
  - `edit → compile` (refactors, config changes)
  - `add failing test → run-fail → implement → run-pass` (TDD slices — EditMode only, see the runner rules below)
  - `grep → confirm zero hits` (verification phases)
  Each step must be a real action (a concrete code change, or a runnable command with `Run:` / `Expected:`), never a description.
- The Skill bullet must name a skill from `plan.md` Part 2. If none applies, write `Skill: none — <one-line reason>`.
- The closing phase is named `## Phase N — Final verification` and contains only no-production-change sanity checks.

**Verification commands — use `.claude/workflow/unity-project.md`.** That file owns the runner table; do not restate commands from memory and do not invent a command that is not in it. Commands run in **PowerShell on Windows** — chain with `;`, not `&&`, and use backslash paths.

Hard constraints worth restating because they change plan shape:

- **`$env:UNITY_EXE` must be set** for any Unity CLI step. If a plan's first Unity step is early in the run, make the very first task a check: `Run: $env:UNITY_EXE` → `Expected: a path to Unity.exe, not empty`. Cheaper than discovering it in phase 4.
- **Unity cannot open the project twice.** Any batchmode step fails while the developer has the Editor open. Plan for it: state in the phase framing that the Editor must be closed for the test steps.
- **`dotnet build` needs the generated `.sln` to exist.** If the project has never been opened in the Editor, it will not. Prefer a scoped EditMode run as the compile gate in that case.
- **PlayMode tests only where a frame loop is genuinely required.** Default every test to `Assets/Tests/EditMode/`. Planning a PlayMode test for logic that could be plain C# is a design smell — push the logic out of the MonoBehaviour instead, and say so in the plan.
- **Test results are read from the `-testResults` XML**, not from the log tail. Write `Expected:` in terms of that file.
- **There is no lint script and no analyzer.** Never plan one.
- Unfiltered full-suite runs belong only to the Final verification phase; `/fb-apply` delegates them to QA.

**Serialized-field and asset changes have a mandatory task shape.** Because serialization is name-based and invisible to the compiler:

1. A task that changes the C# side, carrying `[FormerlySerializedAs("<old>")]` for every renamed field the Step 1.6 audit found hits for.
2. A separate task — `Skill: none — Editor operation the developer owns` — where the **developer re-saves the affected prefabs/scenes/assets in the Editor** so the migrated values are written to disk, and re-wires any Inspector reference the change invalidated. This task lists every affected asset path from the audit.
3. Only then any task that removes the `[FormerlySerializedAs]` attribute — and normally that is a follow-up contract, not this one.

Never plan a step that hand-edits a `.prefab`, `.unity`, or `.asset` file's YAML to fix a reference. A wrong `fileID` corrupts the asset silently.

**Other rules:**

- One component per task. If a slice touches a controller, a data type, and a test asmdef, that's separate tasks under the same phase — not one bundle.
- If the work warrants TDD (new logic with a meaningful invariant), the task's steps follow the test-first sequence. If it's a mechanical refactor, rename, or config edit, the steps follow edit/verify. The planner picks the shape per task.
- **Prefer plain C# for anything with a testable invariant.** A task that puts branching logic inside a `MonoBehaviour` when it could live in a plain class has made itself untestable in EditMode; the plan should note why if it does that deliberately.

**How phases execute in `/fb-apply`:**
- The Implementer subagent walks every phase end-to-end first, executing every `- [ ] **Step:**` bullet of every task in order — including test steps. Reviewers do **not** run between phases.
- After the last phase, three reviewers (Code-Evaluator + Defender + QA) run **once, in parallel**, against the cumulative implementation. QA validates the production code AND any tests introduced.
- If reviewers find issues, the Implementer gets a single combined fix prompt, then reviewers run **one** verification round. Max 2 rounds total.

### Rules across both files
- `plan.md` Part 1 is the alignment check, Part 2 is the technical approach, and `tasks.md` is the execution list. Don't duplicate content across them.
- Tasks must be specific: file paths, class names, method names, component names, asset paths.
- Tests live inside the task that introduces the behaviour they cover. Tasks that introduce new logic with a meaningful invariant must include a test step (and the corresponding `Test:` entry in the `**Files:**` block).
- The plan must comply with the loaded skills' standards, every applicable `.claude/rules/` file, and the traps section of `.claude/workflow/unity-project.md`.

### No placeholders
Every line must contain content the developer can act on. These are **plan failures** — never write them in either file:
- "TBD", "TODO", "implement later", "fill in details"
- "Add appropriate error handling" / "add validation" / "handle edge cases"
- A step that is prose ("verify it works", "run the build") without a `Run:` / `Expected:` line or a concrete code block
- A step that describes *what* without showing *how*
- References in `tasks.md` to types or methods not present in `plan.md` Part 2 "Data shapes" or earlier tasks
- An empty `mermaid` code fence in `plan.md`
- A `plan.md` section with no body (write the one-line skip justification instead)
- A `## Phase` heading with no framing paragraph, or with no `### Task N:` blocks under it
- A task missing its `- Skill:` line, its `**Files:**` block, or any `- [ ] **Step:**` bullet
- A step that hand-edits `.prefab` / `.unity` / `.asset` YAML
- A step invoking a linter or analyzer — none exists
- A `Skill:` value naming a skill that does not exist on disk

### Cross-file consistency
- Every code-touching task in `tasks.md` carries a `**Files:**` block and at least one `- [ ] **Step:**` bullet — file paths and verification commands are owned by tasks, not by `plan.md`.
- Every `- Skill:` value in a task must appear in `plan.md` Part 2 "Skills to invoke during execution" (or be the literal `none — <reason>`).
- Every type, serialized field, method signature, and asset path used inside a task's steps must match `plan.md` Part 2 "Data shapes" (or be introduced by an earlier task).
- Every "In scope" bullet in `plan.md` Part 1 must map to one or more tasks in `tasks.md`.
- Every assumption in `plan.md` Part 1 that constrains a technical decision must be reflected in Part 2 "Approach" or "Risks and judgement calls".
- Every affected asset named in the Step 1.6 audit appears either in a task's `**Files:**` block or in the developer-wiring task.
- Every phase in `tasks.md` ends compiling with no half-applied changes — confirm this in the Self-review block.
