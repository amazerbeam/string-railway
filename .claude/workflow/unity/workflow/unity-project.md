# Unity project layout, runners, and Editor-owned work

The canonical statement of **where code lives**, **how to verify it**, and **what only the developer can do**. `/fb-plan` reads it to write runnable `Run:` steps; `/fb-apply` and the four agents read it instead of carrying their own copies of the paths.

Change a path or a command **here only**. A runner stated in five files gets updated in four.

> **Status: assumed, not yet observed.** This project had no Unity project on disk when the workflow was installed, so the layout below is the Unity default and the commands are the standard CLI invocations. Correct anything that turns out wrong the first time you run `/fb-apply`, and the whole pipeline follows.

## Layout

```
<repo root>/
  Assets/
    Scripts/              gameplay + systems code (asmdef per feature area)
    Tests/
      EditMode/           NUnit tests, no scene load — the fast gate
      PlayMode/           NUnit tests that run in a live player loop
    Prefabs/  Scenes/  Art/  Audio/  Settings/
  Packages/
    manifest.json         package dependencies — the only sanctioned dependency list
  ProjectSettings/        layers, tags, input, build targets, quality
  *.sln  *.csproj         GENERATED by Unity — never hand-edit, never commit-worthy as source
```

- Every asset has a sibling `.meta` file holding its GUID. **The `.meta` is not a build artifact** — scenes and prefabs reference assets by that GUID, so a `.meta` that is deleted, regenerated, or moved without its asset silently breaks every reference to it.
- `Assets/Scripts/**` is the only tree where production C# belongs. `Assets/Tests/**` is the only tree where tests belong.
- `Library/`, `Temp/`, `Logs/`, `Build/`, `obj/`, `*.sln`, `*.csproj` are generated. Never plan an edit to them and never treat one as evidence of source state.

## Assembly definitions

Each feature area under `Assets/Scripts/` carries an `.asmdef`; test folders carry their own referencing the production asmdefs plus `UnityEngine.TestRunner` / `UnityEditor.TestRunner`.

This matters for planning: **a test can only see a production assembly its asmdef references.** A task that adds a test for a type in a new assembly must also add that assembly reference, or the test will not compile. Treat a missing asmdef reference as part of the task, not a follow-up.

## Verification commands

Commands run in **PowerShell on Windows**. Chain with `;`, never `&&`. Use backslash paths.

The Unity Editor executable is machine-specific and is **not** on `PATH`. Every CLI invocation goes through `$env:UNITY_EXE`, which the developer sets once:

```powershell
$env:UNITY_EXE = "C:\Program Files\Unity\Hub\Editor\<version>\Editor\Unity.exe"
```

| To verify | Command |
|---|---|
| Code compiles (fast, no Editor lock) | `dotnet build StringsAndStations.sln` |
| EditMode tests | `& $env:UNITY_EXE -runTests -batchmode -projectPath . -testPlatform EditMode -testResults TestResults-EditMode.xml -logFile -` |
| PlayMode tests | `& $env:UNITY_EXE -runTests -batchmode -projectPath . -testPlatform PlayMode -testResults TestResults-PlayMode.xml -logFile -` |
| One test class / fixture | append `-testFilter <Namespace.ClassName>` to either of the above |
| A file exists | `Get-ChildItem <path>` |
| A pattern is gone | `Select-String -Path <glob> -Pattern "<pattern>"` → Expected: zero hits |
| An asset's GUID | `Get-Content <path>.meta \| Select-String guid` |

### Hard constraints on runners

- **Unity holds an exclusive lock on the project folder.** A `-batchmode` run fails with `Multiple Unity instances cannot open the same project` while the Editor is open on this project. This is the single most common false failure in the pipeline: treat that message as "developer has the Editor open", ask them to close it, and re-run — never as a code defect.
- **`dotnet build` requires the `.sln` / `.csproj` to already exist.** Unity generates them on import. If they are absent, the fast compile gate is unavailable — fall back to an EditMode test run, which forces a full compile, and say that you did.
- **Test results land in an XML file, not on stdout.** `-logFile -` streams the Editor log; the pass/fail counts come from parsing the `-testResults` XML. Read that file — do not judge the run from the log tail alone. The process exit code is `0` only when every test passed.
- **There is no lint script and no analyzer** wired into this project. Never invent `dotnet format --verify-no-changes` or an analyzer run as a required gate unless one has actually been added.
- **PlayMode tests are slow and flaky under load** — they spin a real player loop. Reserve them for behaviour that genuinely needs a frame loop (physics, coroutines, animation, scene lifecycle). Anything expressible as a pure-C# assertion belongs in EditMode.
- Full-suite runs (both platforms, unfiltered) belong **only** to QA in the closing `Final verification` phase. The Implementer runs `-testFilter`-scoped runs.

## Developer-owned Editor work

Some work cannot be done from a file edit, because the state lives in a binary/YAML asset that Unity owns and rewrites. **Never dispatch these to the Implementer and never attempt them by hand-editing the asset** — a hand-edited scene or prefab with a wrong `fileID` corrupts silently and is painful to unpick.

The Implementer writes the code; the developer wires it in the Editor:

- Assigning `[SerializeField]` / Inspector references on a prefab or scene object
- Adding a scene to **Build Settings** (a scene absent from that list cannot be loaded at runtime, and the failure only appears in a player build)
- Creating or assigning `ScriptableObject` instances
- Layers, tags, sorting layers, physics collision matrix, Input System action maps — all `ProjectSettings/`
- Import settings on art/audio (atlases, compression, rig config)
- Any change that requires observing the game running

Treat reaching one of these as a **pause condition**, exactly like a schema migration: stop dispatching, state precisely what the developer must click and where, wait for confirmation, then continue.

## Unity-specific correctness traps

These produce bugs that compile cleanly and pass a naive review. Planning and review must account for them.

- **Renaming a `[SerializeField]` field discards its serialized value** on every prefab, scene object, and asset that held one. The fix is `[FormerlySerializedAs("oldName")]` on the renamed field, kept until the assets have been re-saved. A rename without it is data loss, not a refactor.
- **A `MonoBehaviour` class name must match its filename.** Renaming the class without renaming the file (or vice versa) unbinds the script from every object using it — they show up as "missing script".
- **Destroyed `UnityEngine.Object`s are not `null`, they are fake-null.** `Object` overloads `==` to report destroyed objects as equal to `null`, but `?.`, `??`, and `is null` bypass that operator and see a live reference. `transform?.position` on a destroyed object throws. Use explicit `if (obj != null)` on Unity types.
- **`Awake` / `OnEnable` / `Start` ordering across objects is not guaranteed.** Code that reads another object's state in `Awake` is a race. `Start` for cross-object reads, `Awake` for self-initialisation.
- **`Update` runs every frame** — allocations there (LINQ, string concatenation, `GetComponent`, `Find`, boxing, closures) are the GC-pressure equivalent of an N+1 query. Cache in `Awake`, allocate outside the loop.
- **Frame-rate coupling**: movement and timers must scale by `Time.deltaTime`; physics forces belong in `FixedUpdate` with `Time.fixedDeltaTime`. Applying a force in `Update` gives frame-rate-dependent behaviour that looks fine at 60fps and breaks at 144.
- **Static state survives Play-mode exit** when *Enter Play Mode Options* has domain reload disabled, and always survives between EditMode tests in one run. A static field that is not explicitly reset leaks between tests and between play sessions.
- **Coroutines die with their host `GameObject`**, mid-body, without running the rest of the method — including anything after a `yield` that was meant to clean up. `finally` blocks do not save you if the object is destroyed.
- `Resources/` is loaded eagerly into the build. Prefer Addressables or direct references for anything large.
